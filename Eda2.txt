# OpenShift Virtualization — Disconnected Bare-Metal EDA Scenario Catalog

Covers **Initiative 2 (Event-Based Actions)**, **Initiative 3 (Adhoc / Day-2 On-Demand)**, **Initiative 4 (Change Management & Approval-Gated Workflows)**, and **Initiative 5 (Fleet-Wide / Multi-Cluster Orchestration)** — the two highest-priority gaps identified when auditing the original three initiatives. Initiative 1 (platform alerts diagnostics & remediation) is out of scope here since it's an existing pipeline — flag if you want it catalogued the same way. Scheduled/preventive maintenance, Day-0/1 cluster bring-up, subscription compliance, and GitOps drift reconciliation remain uncatalogued; say the word if you want any of those next.

## 0. Scope & Assumptions

```
Alertmanager ──(webhook)──> Kafka[alertmanager-ocpv-events] ──> EDA Rulebook ──> AAP Job Template ──> Playbook ──> Kafka[ocpv-ansible-results]
Portal(Day-2 UI) ──(publish)──> Kafka[ocpv-adhoc-requests]     ──> EDA Rulebook ──> AAP Job Template ──> Playbook ──> Kafka[ocpv-ansible-results]
```

- **Stack assumed**: Metal3/BMO (bare-metal lifecycle), ODF or LVMS (storage), MetalLB (LB), kubernetes-nmstate (host networking / NNCP), OADP (backup), cert-manager (internal PKI), oc-mirror + OSUS (disconnected registry/updates), MTV (VM import), Strimzi Kafka / Kafka Bridge (since you're already on OCP). Swap names if your build differs.
- **Two event shapes feed the same Kafka pipeline**:
  - **Alert-native** — a PrometheusRule/Alertmanager alert fires on a metric threshold. Clean fit for the alert→Kafka path you already have.
  - **State-transition** — several triggers below (BareMetalHost phase, DataVolume import success, etc.) are Kubernetes object state changes, not natively alerts. These need either a small recording-rule/exporter that turns the state into a Prometheus alert, or a parallel watch source feeding the same result topic. Flagged per-scenario in the tables so you can decide.
- **Adhoc requests** are modeled as a second Kafka topic (`ocpv-adhoc-requests`) published by the portal, so both initiatives share one EDA engine and one result contract. If your portal calls the AAP Controller API directly instead, drop the Kafka hop — the job-template/playbook layer is unaffected.
- **Disconnected constraint**: every collection/module referenced below (`kubernetes.core`, `kubevirt.core`, `community.general`, etc.) must be pre-baked into your AAP Execution Environment image — no dynamic collection installs.
- **Initiative 4 adds**: AAP Workflow Templates with native Approval nodes (primary pattern) — no new infrastructure needed since it's a platform feature you already have. An external-ITSM-gated alternate is included for shops where CAB approval must live outside AAP.
- **Initiative 5 adds**: Red Hat Advanced Cluster Management (ACM) as the hub — `ManagedCluster`/`PolicyViolation` objects for fleet visibility, and Topology Aware Lifecycle Manager (TALM) as the production-grade mechanism for canary-wave cluster upgrades specifically (our hand-rolled orchestrator pattern is the general-purpose version for everything that isn't a ClusterVersion upgrade).
- **IDs**: `EVT-##` = event-based (23), `ADH-##` = adhoc (46), `CHG-##` = change-gated (18), `FLT-##` = fleet campaign (12). 99 scenarios across four initiatives.

## 1. How This Document Is Organized

- **§2** — full scenario catalog, grouped by subsystem, one small table per group
- **§3** — the reusable execution patterns: §3.1–3.3 for event/adhoc (direct-execute), §3.4 for change-gated (approval required before execute), §3.5 for fleet (campaign/wave execute)
- **§4** — Kafka schemas: the base job-result contract, plus extensions for change requests (§4.1) and campaigns (§4.2)
- **§5** — fully worked pseudocode for **20 representative scenarios** (one per subsystem group across Initiatives 2–4). Every other scenario reuses the matching pattern from §3 — only the task block or config changes, and each table row gives you what you need to write it. Initiative 5's variety is entirely config-driven (§3.5's config table), so it doesn't need separate worked examples.

### 2.3 Initiative 4 — Change Management & Approval-Gated Workflows

Same intake mechanics as Initiatives 2/3 (an alert or a portal request), but the resource/action is sensitive enough that it must **pause for human sign-off** before the job template runs. Architecturally distinct — see §3.4.

*Pseudocode legend: "§3.4 pattern" = reuse the generic pattern with a different target job template · §5.1x = fully worked example.*
