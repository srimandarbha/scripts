# OpenShift Virtualization — Disconnected Bare-Metal EDA Scenario Catalog

Covers **Initiative 2 (Event-Based Actions)** and **Initiative 3 (Adhoc / Day-2 On-Demand)**. Initiative 1 (platform alerts diagnostics & remediation) is out of scope here since it's an existing pipeline — flag if you want it catalogued the same way.

## 0. Scope & Assumptions

```
Alertmanager ──(webhook)──> Kafka[alertmanager-ocpv-events] ──> EDA Rulebook ──> AAP Job Template ──> Playbook ──> Kafka[ocpv-ansible-results]
Portal(Day-2 UI) ──(publish)──> Kafka[ocpv-adhoc-requests]     ──> EDA Rulebook ──> AAP Job Template ──> Playbook ──> Kafka[ocpv-ansible-results]
```

- **Stack assumed**: Metal3/BMO (bare-metal lifecycle), ODF or LVMS (storage), MetalLB (LB), kubernetes-nmstate (host networking / NNCP), OADP (backup), cert-manager (internal PKI), oc-mirror + OSUS (disconnected registry/updates), MTV (VM import), Strimzi Kafka / Kafka Bridge (since you're already on OCP). Swap names if your build differs.
- **Two event shapes feed the same Kafka pipeline**:
  - **Alert-native** — a PrometheusRule/Alertmanager alert fires on a metric threshold. Clean fit for the alert→Kafka path you already have.
  - **State-transition** — several triggers below (BareMetalHost phase, DataVolume import success, etc.) are Kubernetes object state changes, not natively alerts. These need either a small recording-rule/exporter that turns the state into a Prometheus alert, or a parallel watch source feeding the same result topic. Flagged per-scenario in the tables so you can decide.
- **Adhoc requests** are modeled as a second Kafka topic (`ocpv-adhoc-requests`) published by the portal, so both initiatives share one EDA engine and one result contract. If your portal calls the AAP Controller API directly instead, drop the Kafka hop — the job-template/playbook layer is unaffected.
- **Disconnected constraint**: every collection/module referenced below (`kubernetes.core`, `kubevirt.core`, `community.general`, etc.) must be pre-baked into your AAP Execution Environment image — no dynamic collection installs.
- **IDs**: `EVT-##` = event-based (23 total), `ADH-##` = adhoc (46 total). 69 scenarios.

## 1. How This Document Is Organized

- **§2** — full scenario catalog, grouped by subsystem, one small table per group
- **§3** — the common EDA rulebook pattern + common playbook skeleton every scenario reuses
- **§4** — the common Kafka result-topic schema
- **§5** — fully worked pseudocode for **15 representative scenarios** (one per subsystem group). The other 54 scenarios reuse the exact same skeleton (§3.3) — only the task block changes, and each table row gives you the Job Template name + Action Summary needed to write it.

## 3. Common Patterns

### 3.1 EDA Rulebook — Event-Based (Initiative 2)

```yaml
---
- name: OCP Virt Disconnected BM - Event-Based Actions
  hosts: all
  sources:
    - ansible.eda.kafka:
        host: "{{ kafka_bootstrap_host }}"
        port: "{{ kafka_port }}"
        topic: "alertmanager-ocpv-events"
        group_id: "eda-ocpv-baremetal-events"
        security_protocol: "SASL_SSL"
        sasl_mechanism: "SCRAM-SHA-512"
        sasl_username: "{{ kafka_user }}"
        sasl_password: "{{ kafka_password }}"
        cafile: "{{ internal_ca_bundle }}"   # disconnected: internal CA, not public

  rules:
    - name: EVT-01 Post-upgrade validation
      condition: >
        event.payload.labels.alertname == "OCPVirtUpgradeCompleted"
        and event.payload.status == "firing"
      action:
        run_job_template:
          name: "jt-ocpv-postupgrade-validate"
          organization: "OCP-Virt"
          job_args:
            extra_vars:
              correlation_id: "{{ event.payload.fingerprint }}"
              cluster: "{{ event.payload.labels.cluster }}"

    - name: EVT-06 BareMetalHost Error diagnostics
      condition: >
        event.payload.labels.alertname == "BareMetalHostError"
        and event.payload.status == "firing"
      action:
        run_job_template:
          name: "jt-ocpv-bmh-error-diag"
          organization: "OCP-Virt"
          job_args:
            extra_vars:
              correlation_id: "{{ event.payload.fingerprint }}"
              bmh_name: "{{ event.payload.labels.bmh_name }}"
              bmh_namespace: "{{ event.payload.labels.namespace }}"

    # ... one rule block per remaining EVT-## row, same shape:
    # match on labels.alertname, run its Job Template, pass identifying labels as extra_vars
```

### 3.3 Common Playbook Skeleton

Every scenario — event-based or adhoc — wraps its unique logic in this shape. §5 only shows the highlighted task block per scenario; everything else below is boilerplate you write once and reuse.

```yaml
---
- name: "<scenario> - common execution skeleton"
  hosts: localhost
  gather_facts: false
  vars:
    kafka_result_topic: "ocpv-ansible-results"
    # Kafka writes below assume a Strimzi Kafka Bridge / REST Proxy HTTP endpoint,
    # since that avoids baking a Python Kafka client into the EE. Swap for a
    # custom module if you have one.

  tasks:
    - name: Publish IN_PROGRESS to Kafka result topic
      ansible.builtin.uri:
        url: "{{ kafka_bridge_url }}/topics/{{ kafka_result_topic }}"
        method: POST
        headers: {Content-Type: "application/vnd.kafka.json.v2+json"}
        body_format: json
        body:
          records:
            - value:
                correlation_id: "{{ correlation_id }}"
                scenario_id: "<EVT-## | ADH-##>"
                status: "IN_PROGRESS"
                started_at: "{{ ansible_date_time.iso8601 }}"
                aap_job_id: "{{ tower_job_id | default(awx_job_id) | default('') }}"

    - block:
        - name: Idempotency / pre-check guard
          # e.g. "does the target already exist / already match desired state?"
          # skip the main block if so, publish SKIPPED_IDEMPOTENT instead of SUCCESS

        # ============================================================
        # === SCENARIO-SPECIFIC TASK BLOCK — this is what §5 shows ===
        # ============================================================

        - name: Post-validation - confirm desired end state reached
          ansible.builtin.assert:
            that: "<end-state condition>"

      rescue:
        - name: Capture failure context
          ansible.builtin.set_fact:
            failure_reason: "{{ ansible_failed_result.msg | default('unknown') }}"

        - name: Publish FAILED result to Kafka
          ansible.builtin.uri:
            url: "{{ kafka_bridge_url }}/topics/{{ kafka_result_topic }}"
            method: POST
            headers: {Content-Type: "application/vnd.kafka.json.v2+json"}
            body_format: json
            body:
              records:
                - value:
                    correlation_id: "{{ correlation_id }}"
                    status: "FAILED"
                    summary: "{{ failure_reason }}"
                    completed_at: "{{ ansible_date_time.iso8601 }}"

        - name: Fail the play so AAP marks the job failed
          ansible.builtin.fail:
            msg: "{{ failure_reason }}"

      always:
        - name: Publish SUCCESS result to Kafka (only reached if rescue didn't fire)
          ansible.builtin.uri:
            url: "{{ kafka_bridge_url }}/topics/{{ kafka_result_topic }}"
            method: POST
            headers: {Content-Type: "application/vnd.kafka.json.v2+json"}
            body_format: json
            body:
              records:
                - value:
                    correlation_id: "{{ correlation_id }}"
                    status: "SUCCESS"
                    summary: "<one-line outcome>"
                    completed_at: "{{ ansible_date_time.iso8601 }}"
          when: ansible_failed_task is not defined
```

## 4. Kafka Result-Topic Schema

One shape, used by every playbook, so downstream consumers (dashboards, ITSM, the portal) parse a single contract:

```json
{
  "correlation_id": "alert fingerprint (event-based) or portal request_id (adhoc)",
  "initiative": "event_based | adhoc",
  "scenario_id": "e.g. EVT-13 or ADH-23",
  "job_template": "string",
  "aap_job_id": 12345,
  "target": {
    "cluster": "string",
    "namespace": "string",
    "resource_kind": "VirtualMachine | BareMetalHost | Node | ...",
    "resource_name": "string"
  },
  "status": "IN_PROGRESS | SUCCESS | FAILED | SKIPPED_IDEMPOTENT",
  "started_at": "ISO8601",
  "completed_at": "ISO8601",
  "summary": "one-line outcome",
  "details": { "...task-specific key/values..." },
  "requested_by": "portal user (adhoc only)",
  "artifacts": ["optional: must-gather URL, log bundle URL, report URL"]
}
```

Never put secrets (e.g. a reset password) in this payload — see §5.12 for the pattern.

## 5. Worked Pseudocode (15 Representative Scenarios)

Each block below is the **scenario-specific task block** that slots into §3.3. Module names are illustrative pseudocode — validate against what's actually in your EE.

### 5.1 EVT-01 — Post-upgrade validation suite

```yaml
- name: Gather ClusterOperator status
  kubernetes.core.k8s_info:
    api_version: config.openshift.io/v1
    kind: ClusterOperator
  register: cluster_operators

- name: Assert no ClusterOperator is Degraded / all Available
  ansible.builtin.assert:
    that:
      - (item.status.conditions | selectattr('type','equalto','Degraded') | map(attribute='status') | first) == "False"
      - (item.status.conditions | selectattr('type','equalto','Available') | map(attribute='status') | first) == "True"
    fail_msg: "ClusterOperator {{ item.metadata.name }} unhealthy post-upgrade"
  loop: "{{ cluster_operators.resources }}"
  loop_control: {label: "{{ item.metadata.name }}"}

- name: Confirm all nodes Ready
  kubernetes.core.k8s_info: {kind: Node}
  register: nodes
- ansible.builtin.assert:
    that: "item.status.conditions | selectattr('type','equalto','Ready') | map(attribute='status') | first == 'True'"
  loop: "{{ nodes.resources }}"

- name: Check HyperConverged CR health
  kubernetes.core.k8s_info:
    api_version: hco.kubevirt.io/v1beta1
    kind: HyperConverged
    name: kubevirt-hyperconverged
    namespace: openshift-cnv
  register: hco
- ansible.builtin.assert: {that: "hco.resources[0].status.conditions | ... all healthy"}

- name: Test image pull against local mirror registry
  kubernetes.core.k8s:
    state: present
    definition: "<throwaway Pod pulling a known local-mirror image>"
  register: pull_test
- name: Clean up pull-test pod
  kubernetes.core.k8s: {state: absent, definition: "{{ pull_test }}"}

- name: Boot smoke-test one VM per StorageClass
  loop: "{{ storage_classes_to_test }}"
  block:
    - kubevirt.core.kubevirt_vm: {state: present, name: "smoketest-{{ item }}", ...}
    - name: Wait for Running
      kubernetes.core.k8s_info: {api_version: kubevirt.io/v1, kind: VirtualMachineInstance, name: "smoketest-{{ item }}"}
      register: vmi
      until: vmi.resources[0].status.phase == 'Running'
      retries: 20
      delay: 10
    - kubevirt.core.kubevirt_vm: {state: absent, name: "smoketest-{{ item }}"}

- name: Live-migration re-test on a canary VM
  kubernetes.core.k8s:
```

## 6. Extending This Pattern

- **New event-based scenario**: add/confirm a PrometheusRule (or bridge a K8s state change into one) → add a rule block to the §3.1 rulebook matching its `alertname` → create `jt-ocpv-<subsystem>-<action>` → wrap the task in the §3.3 skeleton → add a row to §2.1.
- **New adhoc scenario**: have the portal emit a `request_type` → add a rule block to §3.2 → create the Job Template → wrap the task in the skeleton → add a row to §2.2.
- Keep `correlation_id` flowing end-to-end (alert fingerprint or portal `request_id`) — it's what lets the Kafka result-topic record join back to the originating alert/request.
- Keep the `jt-ocpv-<subsystem>-<action>` naming convention consistent — it keeps AAP RBAC/scoping simple as the catalog grows past 69 scenarios.
