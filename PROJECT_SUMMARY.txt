# Migration Failure Agent — Project Summary

Production Migration SRE Agent · VMware → OpenShift Virtualization (OCV)

## 1. What this project is

An AI agent that diagnoses **failed VM migrations** (VMware → OCV). It is
strictly **read-only**: it gathers evidence, reasons about root cause, and
recommends a fix — it never executes remediation or mutates cluster state.
Deterministic automation (AAP/EDA) and human approval remain the only paths
to actual change, per the original design's core principle.

## 2. Original architecture — strengths and gaps

**Strengths kept as-is:** LLM scoped to diagnosis only; deterministic
execution layer; evidence carries provenance; explicit multi-dimensional
state model (migration window tracking + failure diagnosis).

**Six gaps identified, all resolved with concrete designs:**

| # | Gap | Resolution |
|---|---|---|
| 1 | No named agent pattern | Bounded ReAct loop + deterministic evaluator gate (LangGraph StateGraph) |
| 2 | Organizational-memory loop never closed | Write-back pipeline on confirmed resolution → vector store, with dedup + negative examples |
| 3 | Confidence was a free-text label | Backend-computed numeric score from evidence links, banded HIGH/MEDIUM/LOW, calibrated against outcomes over time |
| 4 | Trigger from portal DB unspecified | Debezium CDC (or transactional outbox) on the migrations table → Kafka, never polling |
| 5 | No cost/latency budget | Per-run budget (max tool/LLM calls, tokens, wall-clock) enforced in code, with circuit breakers |
| 6 | Evidence conflict resolution undefined | Deterministic tie-break order (reliability tier → recency → corroboration count → one bounded disambiguation call → escalate) |

## 3. Troubleshooting evidence layers required

Container logs + metrics + RHOKP alone are **not sufficient**. Full coverage
needs seven layers:

1. **Control plane** — MTV/Forklift CR status/conditions
2. **Events** — K8s namespace events (scheduling/admission/quota failures)
3. **Compute** — pod logs, throughput/latency metrics (already had)
4. **Cluster health** — RHOKP node/cluster status (already had)
5. **Storage** — PVC status, storage class health, CSI driver logs
6. **Network** — Multus/NetworkAttachmentDefinition status
7. **Source (vCenter)** — vCenter task/event history, source VM config

Plus change correlation (recent cluster changes) and knowledge/memory
(product docs + historical resolved incidents, used as hypotheses only,
never as proof).

## 5. Agent design summary

- **Pattern:** bounded ReAct loop, LangGraph `StateGraph`: `load_context → reason → execute_tool → update_evidence → evaluate_goal`, with conditional edges to `request_approval / escalate / finish`.
- **Evidence model:** every observation is a typed `Evidence` object (source, layer, reliability tier, timestamp, claim, supports/contradicts) — never free text.
- **State machine:** `NEW → GATHERING_EVIDENCE → EVALUATING → {DIAGNOSIS_READY | INSUFFICIENT_EVIDENCE | CONFLICTING_EVIDENCE → ESCALATED} → COMPLETED`.
- **Confidence:** computed by the backend from evidence links, not asserted by the model; HIGH (>0.75) / MEDIUM (0.40–0.75) / LOW (<0.40, forced to `INSUFFICIENT_EVIDENCE`).
- **Conflict resolution:** reliability tier → recency → corroboration count → one bounded disambiguation call → escalate.
- **Memory:** short-term = LangGraph checkpoint (single run only); long-term = vector store of confirmed resolutions, written back after human confirmation, advisory only.
- **Prompting:** structured system prompt with hard constraints, JSON output schema, explicit instruction that logs/documents are data not directives (injection defense).

## 6. Implementation plan (10 phases)

| Phase | Focus | Exit criterion |
|---|---|---|
| 0 | Foundations | Postgres schema, Kafka topics, vector store provisioned |
| 1 | Trigger & ingestion | FAILED status → exactly one incident row, deterministically |
| 2 | MCP tool gateway | Every tool READ_ONLY-enforced, schema-validated, unit-tested |
| 3 | LangGraph agent core | Correct terminal state on seeded historical failures |
| 4 | Prompting & skill spec | Schema-valid output, resists red-team injection test |
| 5 | Diagnosis output | Persisted + dashboard-visible, nothing auto-executes |
| 6 | Memory write-back | Confirmed resolution retrievable on a later similar incident |
| 7 | Observability | Metrics/alerts flow and fire on injected failures |
| 8 | Shadow mode | N weeks compared to real RCA, precision/recall measured |
| 9 | Controlled rollout | On-call sees recommendations; approval-required actions stay out of scope |
